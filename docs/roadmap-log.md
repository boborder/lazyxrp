# Roadmap log — pivot record and planning cautions

[日本語](roadmap-log-ja.md)

**Role:** Supporting record for [`ROADMAP.md`](../ROADMAP.md). ROADMAP holds the goal hierarchy and priorities; this file holds "why the direction changed" and "planning cautions". Code-level pitfalls and known issues are owned by [`problems.md`](problems.md) (SSOT).

## Cautions (planning cautions)

- **Security is non-negotiable.** Mainnet writes require simulate + `--yes`, seeds/mnemonics go only through `credential_from_secrets`, and the config world-readable warning must not be removed. Never loosen these in pursuit of adoption (popularity). Details in [`security.md`](security.md).
- C3 was verified on testnet (XRPL testnet + Coston2) on 2026-10-11. Running it on mainnet has not been done and is not planned (user decision: real funds stay on testnet). Fetching the FDC proof (verifier `prepareRequest` → `FdcHub` → DA layer) was **a policy pivot on 2026-10-20** (user-approved): `-x fxrp-execute` does everything from fetching through `executeDirectMinting` in one command. The TUI's C3 still uses pasting the proof as before. Reasons and mitigations are in the 2026-10-20 section of [`security.md`](security.md).
- Keymap customization touches `src/config.rs` → under the AGENTS.md contract, every `docs/` file that mentions config keys must be synced in the same change. Built-in defaults live in `config.json5`.
- OfferCancel (formerly F-02) has been merged into DEX trading. It is not pursued as a separate task.

## Pivot log

- **2026-10-24** — Review of the scope of Flare support (user question: "can everything be done with just an XRP wallet?"). Judgment: XRPL signing alone is the default path; an EVM key stays optional (finalizing yourself / EVM-side redeem and tagging). Tracing the code showed gaps in an XRP-only mint: in C2 the recipient hex starts out blank and the personal account is shown truncated to 16 characters, and every `sa-memo` op has a precondition or a side effect. The fixes are to prefill C2's recipient with your own personal account (it is an RPC response, so it is recorded as accepted in S-019 / R-019) and to add a finalize wait to `sa-memo` plus `sa-status`. **Correction**: `sa-call` (`0xFE`) is not an XRP-only path because the public executor does not hold the userOp bytes and cannot finalize it, so `0xFF`, which a public executor can relay, was raised to P2 (subject to confirmation on a real run). Reading mainnet AssetManager events confirmed that a public executor exists (typically 905 / Smart Account 1000+, 95–177 s), but whether a low-fee payment gets picked up has not been measured, so it is not written as "completes with XRP alone", and the confirmation (F4-d) is left awaiting a user decision. `sa-memo` / `sa-call` in the TUI and sending the DA layer API key are deferred.
- **2026-10-24** — Docs restructure and Smart Account persistence decision. Judgment: every docs/*.md and ROADMAP.md now has an English canonical file and a `-ja.md` twin (rule: change both together). ROADMAP is reorganised by area (XRPL / UI-UX / Flare / quality) with a verification-debt table and explicit proposals; the XRPL coverage table stays in ROADMAP.md because `src/coverage.rs` TC-248 reads it. Decision: Smart Account data is not persisted (see architecture §6.9 'Persistence'; only a user-verified `expected_personal_account` pin would be worth storing, ROADMAP F5-b, P3).
- **2026-10-20** — Research on the latest Flare features (Developer Hub + news + vendored skills + mainnet RPC measurements) was reflected in the ROADMAP "Flare adoption plan". The research showed that C2 / C3 are defenceless against the v1.3 mint limits and `DirectMintingPaymentTooSmallForFee` (no minimum-amount guard, delayed treated as success), so F1 became P1. It turned out FDC proof auto-fetch (F3-d) is possible with public APIs alone, but it contradicts the Cautions line "outside lazyxrp", so it was made a policy change **awaiting a user decision**. Implementation not started (plan only).
- **2026-10-16** — Retired OpenSpec (`openspec/`). The human-facing SSOT is unified in `docs/`. Module dependency rules were merged into `docs/directory.md` §3, invariants I-1–I-11 into `docs/security.md`, and Benchmark operations into `docs/maintenance.md`; the other specs were duplicates of docs and were deleted. The `docs/` → `openspec/` link guard (CI / `mise run lint`) became unnecessary and was removed.
- **2026-10-11** — After 0.5.0, separation of long-running Watch / Operate (user choice: the `--watch` flag). Judgment: instead of adding a new mode to the Wallet panel, startup just removes every key from `Config` (`enter_watch_mode`) — with no key, the existing read-only Account panel appears, no composer or key generation exists, and the poll task cannot sign either. A key's address is used as the watch target when `--account` is not given. `-x` signing commands are rejected explicitly rather than relying on a missing-key error. A WATCH indicator in the status bar was deferred (the panel difference tells them apart).
- **2026-10-11** — After 0.4.2 was published, started F-01 AccountDelete from the long-term list (user choice: TUI + CLI `-x account-delete`). Judgment: the destination is classic / X-address like Payment (tag is given via X-address; no dedicated field). Because it is irreversible, the TUI always asks for a `DELETE` confirmation (the same DangerConfirm as SetRegularKey CLEAR, showing the destination). The fee is not computed locally; the simulate autofill (owner reserve 0.2 XRP) is signed — 200000 drops confirmed on testnet. The 256-ledger constraint and owned objects are left to simulate (`tecTOO_SOON` confirmed in practice). The Wallet panel showed only "None" after deletion, so the wording was changed.
- **2026-10-11** — After 0.4.1 was published, mid-term #8 (C3 smoke) was run on testnet with real funds by user decision. It turned out it had never passed through lazyxrp: C2 was rejected in simulate for `MemoFormat: null` (broken since simulate became mandatory in 0.3.0), and C3 called a selector that does not exist (the `bytes data` ABI version). The 2026-09-12 Coston2 success was from an external script; lazyxrp's own code path had not been verified. After the fix, real DA responses became fixtures for TC-230/231. Note: with a 32-byte memo the public executor executes within minutes first, so our own C3 was verified with a 48-byte memo (executor specified).
- **2026-10-11** — Mid-term #5–#7 after 0.4.0 was published. Writing #5's fake WS fixture in the real rippled frame shape revealed that `xrpl_receive` (typed parse into `XRPLResponse`) dropped the stream message `type`, so ledger close / account tx events had **never** been recognised (the TUI had been running on the interval poll alone). Fixed to read raw frames (`Stream<String>`) and confirmed reception on testnet. The same day, `amm_info` was also parsed in ledger-object notation and came back empty on a real response (TC-015). Lesson (reconfirming TC-200): fixtures / mocks copy the real node's response shape exactly. #6 the double-submit guard sits at a single exit of WalletPanel; #7 follows markers (up to 50 pages).
- **2026-10-11** — Carried out mid-term #4 AMM Deposit/Withdraw. Judgment (user choice): deposit is two-asset only (`tfTwoAsset`), withdraw is all (`tfWithdrawAll`) or an LP amount (`tfLPToken`), the pool is typed directly into the composer, and CLI `-x amm-deposit` / `-x amm-withdraw` were added as well. AMMCreate is not built, and the testnet verification pool was created with a throwaway xrpl.js script (user choice). For that reason `tests/testnet_e2e.rs` does not include AMM (it cannot create a pool itself). Note: the currency / issuer of `LPTokenIn` is looked up from `amm_info` (the AMM account is queried, not computed). The picker became 12 rows and does not fit in the wallet panel (about 16 rows on a 40-row terminal), so it scrolls to keep the selected row visible.
- **2026-10-11** — After 0.3.1 was published, mid-term #1 `poll.rs` split (write path moved to `xrpl/submit.rs`, behaviour unchanged) and #3 EscrowCreate were done. The docs said "signing/poll exist, UI not wired", but in fact there was no signing either, and the poll catch-all silently dropped `EscrowCreateSubmit` (the catch-all was removed to prevent recurrence). Judgment (user choice): times are relative (`90s`/`30m`/`2h`/`7d`), CancelAfter is optional, long-term F-03 EscrowFinish/Cancel was pulled forward to complete inside lazyxrp, and CLI `-x escrow-*` is not built (TUI only). Note: an Escrow ledger object may have no `Sequence`, so the `OfferSequence` for Finish/Cancel is looked up from the creating tx (`PreviousTxnID`). In environments without tmux, TUI E2E was done with PTY + pyte.
- **2026-10-11** — Before 0.3.1, the standard shape of an OSS package was put in place: `CHANGELOG.md` (Keep a Changelog; `mise run release` finalises `[Unreleased]`), `SECURITY.md` with private vulnerability reporting, CI verification of the MSRV (1.94.1, previously only declared and unverified, was measured), and excluding internal docs from the crate. Judgment: the library exists to share code between binaries and its public API is only `run` / `run_rp` (docs.rs stays an entry point for usage guidance). A 5-minute cap was added to the CLI's validated wait (so a node outage does not hang scripts).
- **2026-10-11** — Implemented the four 0.3.1 items (faucet, offer-create, validated wait, opt-in E2E) and ran TUI E2E in tmux. Judgment: the env precedence (§6.2) is unchanged, and `server_info.network_id` is checked before signing (user choice). CLI writes wait until validated by default (user choice; the exit code represents the final result, so it works correctly in scripts). `--no-wait` gives the old behaviour. Note: in manual checks, first verify that no endpoint or seed remains in the env (reads pointing at another network look "empty").
